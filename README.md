# FlowCraft — Production-grade BPMN modeler with a custom layout/routing engine and AI-assisted modeling

FlowCraft is a working BPMN 2.0 modeling web app. It is **not** a wrapper around
`bpmn-js`: the model, the BPMN 2.0 XML import/export, the **layered layout
engine**, the **orthogonal obstacle-aware router**, the **back-edge / loop
handling**, the **validation engine** and the **AI text-to-BPMN + instruction
pipeline** are all custom TypeScript, framework-agnostic, and unit-tested.

The rendering canvas is a custom SVG editor with pan/zoom/grid/snap, marquee and
multi-select, drag with live re-routing, quick-connect, inline labels, undo/redo,
import/export, cleanup actions, light/dark mode, validation, and an AI panel that
generates and updates diagrams from natural language.

## Quick start

```bash
npm install
npm run dev        # http://localhost:5173
npm test           # 35 engine tests (vitest, headless)
npm run build      # type-check + production bundle
npm run typecheck  # strict tsc, no emit
```

Try it: open the app → **AI Modeling** tab → keep the sample text → **Generate
BPMN draft**. Then type an instruction such as *“Add an approval by the manager
before the payment is scheduled”* and click **Apply**. Export to `.bpmn` and
re-import it — geometry, conditions and lanes round-trip.

Sample inputs live in [`samples/ai-prompts.md`](samples/ai-prompts.md); ready
made `.bpmn` files (generated by the engine, with real DI geometry) are in
[`samples/`](samples/).

## 1. Open-source analysis (Phase 1)

| Library | Solves well | Not good enough for this product | Decision |
|---|---|---|---|
| **bpmn-js** | Mature rendering & editing of BPMN, BPMNDI, moddle model, palettes/context-pads | Heavy, hard to deeply customize routing/layout; routing is connection-docking + manual bends, not obstacle-aware; auto-layout is not its job; difficult to inject an AI pipeline or a custom internal representation | **Not used.** Building on it would make the product “mostly a wrapper” and would block the routing/layout quality that is the core requirement. We render with our own SVG layer instead. |
| **diagram-js** | Solid interaction primitives (canvas, dragging, selection) used by bpmn-js | Same coupling concerns; its `LayoutConnection`/cropping produces simple Manhattan routes, no crossing minimisation, no loop-aware channels | **Not used directly.** We re-implemented the interaction surface we need (drag, marquee, connect, zoom/pan) in ~300 lines so routing/layout are fully ours. |
| **bpmn-auto-layout** | Lightweight, turns headless BPMN into a placed diagram by walking the flow | Greedy flow-walk; degrades on joins, re-merging parallel branches and loops; back edges become long ugly lines; not crossing-aware; not lane-aware in a strong way | **Replaced** with a proper layered (Sugiyama-style) layout: rank assignment ignoring back edges, weighted-median crossing reduction, barycenter coordinate assignment with overlap resolution, lane-banded placement. |
| **dagre / elkjs** | High-quality layered/orthogonal layout | dagre is unmaintained and not BPMN/lane/back-edge aware; elk is large, async (worker), and still needs heavy adaptation for BPMN gateways/lanes/back-edges/ports | **Not used.** We implement the specific layered passes we need so behaviour is deterministic, synchronous, testable, and tuned for BPMN reading direction and loops. |
| **fast-xml-parser** | Fast, dependency-light XML parsing | (not a layout/routing concern) | **Used** for import only; export is a custom deterministic writer for clean, diff-friendly, DI-complete output. |
| **zustand** | Minimal, predictable state | — | **Used** for editor state + history wiring. |

**What we extend / build from scratch:**
- Custom **internal model** (`src/core/model`) — small, strongly typed, stable.
- Custom **layered layout** with back-edge-aware ranking and swimlane bands.
- Custom **orthogonal router**: direction-aware A* with a turn penalty + a
  dedicated **back-edge channel** strategy (the single biggest readability win).
- Custom **BPMN 2.0 XML** importer/exporter incl. BPMNDI, lanes, pools, message
  flows, event definitions, markers, conditions and default flows.
- Custom **validation** engine (scopes, gateways, events, readability).
- Custom **AI pipeline** (NL → IR → BPMN) that never lets the model write to the
  canvas directly.

## 2. Architecture decision (Phase 1)

- **Stack:** TypeScript + React 18 + Vite. Vitest for headless engine tests.
- **BPMN base:** none — own normalized model + own renderer. This is the
  deliberate choice that makes “better routing than the average OSS editor”
  achievable and provable.
- **Layout:** layered/Sugiyama (longest-path ranks with back edges removed →
  median crossing reduction → barycenter Y with hard overlap resolution →
  lane-banded variant). Deterministic and synchronous.
- **Routing:** uniform-grid, **direction-aware A\*** with turn penalty for
  forward edges (orthogonal, dodges shapes, minimises bends + crossings) and a
  **deterministic channel router** for back edges (each loop folds into its own
  horizontal lane beneath the content, fanned so loops never stack). Ports are
  fanned along node sides for clean gateway splits/joins.
- **AI pipeline:** `input → segment → classify → role/system/data detection →
  branch & loop detection → IR → BPMN mapping → validate → layout → route →
  review`. Default extractor is deterministic and offline (unit-tested); an
  optional Anthropic-backed extractor (`createAnthropicExtractor`) can produce a
  richer IR but is still constrained to emit IR JSON only.
- **State:** zustand store holding the model + a snapshot-based `History`
  (robust undo/redo with drag coalescing). Clone-on-write keeps React updates
  predictable.
- **Separation of concerns:** rendering (`src/ui`), BPMN logic + AI + routing +
  layout + validation + IO (`src/core/*`), state (`src/state`). The whole
  `src/core` tree has zero React/DOM dependencies and is testable in Node.
- **Technical risks & mitigations:** grid A\* cost on very large diagrams →
  bounded grid + per-scope blocked-grid reuse, back edges bypass A\* entirely;
  NL ambiguity → surfaced as assumptions/ambiguities rather than hallucinated;
  model stability after edits → instructions mutate in place + re-layout, not
  regenerate.
- **Where standard library behaviour is improved:** loop/back-edge routing,
  crossing reduction, lane-aware placement, deterministic output, and an
  auditable AI-to-model mapping with provenance.

## 3. Project structure

```
src/
  core/                 # framework-agnostic engine (no React/DOM)
    model/              # types, factory, graph utils (adjacency, back-edge DFS, topo)
    geometry/           # points, sides, intersection, path simplification
    layout/             # layered Sugiyama layout (+ lane bands) + autoLayout orchestrator
    routing/            # direction-aware A* router + back-edge channel router + message flows
    validation/         # BPMN structural + semantic + readability rules
    xml/                # BPMN 2.0 + BPMNDI import (fast-xml-parser) and export (custom writer)
    ai/                 # types(IR) + extract(NL→IR) + map(IR→BPMN) + instructions + llm hook
    commands/           # snapshot-based undo/redo History
  state/                # zustand editor store (model + history + view + AI)
  ui/                   # SVG canvas, shapes, edges, palette, toolbar, panels, shortcuts
test/                   # vitest suites (engine)
samples/                # generated .bpmn files + AI prompt library
scripts/                # sample generator + Playwright smoke test
docs/                   # architecture notes + screenshots
```

## 4–5. Implementation & tests

See `src/` and `test/`. Run `npm test` — 35 tests cover BPMN import/export,
routing around obstacles, gateway branch fanning, back-edge channels, lane
placement, layout determinism, undo/redo (incl. coalescing & snapshot
isolation), validation rules, text-to-BPMN extraction, and instruction-based
updates (approval, lane split, exception path, node replacement, re-layout).

A Playwright smoke test (`scripts/smoke.mjs`) drives the real app: it generates
a diagram from text (3 → 8 nodes, 3 lanes), applies an instruction (→ 11 nodes),
opens the review panel, and toggles dark mode, asserting no console errors.

## 6. Feature coverage

**BPMN elements:** start/end/intermediate/boundary events (+ message/timer/error/
signal/escalation/terminate definitions), task/user/service/script/send/receive/
manual/business-rule tasks, sub-process (collapsed/expanded), call activity,
exclusive/parallel/inclusive/event-based gateways, sequence/message flows,
associations, data object & data store references, text annotations, pools,
lanes, loop & multi-instance markers, default flows, conditions.

**Modeling UX:** palette, click-to-place, drag-move with live re-routing,
quick-connect handle, marquee + multi-select, inline rename, properties editing,
delete, undo/redo, keyboard shortcuts (Ctrl+Z/Y, Del, Ctrl+A, Esc, +/-, L),
snap-to-grid, zoom-to-cursor, pan, light/dark.

**Quality tools:** *Clean up diagram* (re-layout + re-route), *Clean up flows*
(re-route only), live validation panel with click-to-locate, readability hints.

**AI:** text→BPMN, instruction→update, review panel (roles/systems/documents/
decisions/approvals/checks/loops/exceptions/assumptions/ambiguities + confidence),
provenance (every element traces to source text), ambiguity surfacing.

## Limitations (honest)

- Pools/lanes are modeled and laid out; full pool *resize-by-drag* and
  cross-pool message-flow drawing in the canvas are basic (message flows are
  routed automatically and validated, and import/export them fully).
- The deterministic NL extractor is rule-based; it is strong on SOP/step-list/
  role-prefixed/“if…otherwise” business processes (its target domain) and
  surfaces ambiguity rather than inventing logic. Plug in the Anthropic
  extractor for free-form prose at higher fidelity.
- A\* routing is tuned for diagrams up to a few hundred nodes; beyond that the
  grid step should be increased (a documented knob in `DEFAULT_ROUTING`).
- Expanded sub-process *inline* editing reuses the root scope coordinates;
  drilling into a sub-process as a separate plane is on the roadmap.
